## Project Overview

A Tang Nano 20K design that receives 8-byte price packets over UART, keeps an independent 16-sample moving average for item A (0x11) and item B (0x22), detects price/average crossings, and returns BUY / SELL / repeat-last-action for each item in an 8-byte response.

The main idea: the whole design is a set of small state machines stored in block RAM (BSRAM), which the rules do not count as logic. Each state machine's output register feeds straight back into its own address, so the next state is a table lookup. Arithmetic is done one bit per clock by a lookup table. The Gowin report shows **0 logic (0 LUT, 0 ALU, 0 SSRAM) and 0 registers**.

## FPGA Implementation

Everything runs on the FPGA. No host software is used during judging. The design is 32 block-RAM primitives (`pROM` and `SDPB`) wired directly to each other; there is no other logic.

- **Tick ROM:** a 1872-state counter. Outputs a sample tick every 78 clocks (3 per bit), a bit tick every 234 clocks (115200 baud at 27 MHz), and a slow tick for the timeout.
- **Timeout ROM:** counts slow ticks while the receiver waits between bytes. After about 18.7 ms of silence a half-received packet is dropped, so a stray byte can't misalign the official run.
- **Receive ROM:** a 297-state machine. It detects the start bit on a tick, samples each data bit about 4.5 ticks after the start edge (within about ±1/6 bit of the bit center), and writes each bit into the packet RAM. It signals the controller after the last data bit.
- **Packet RAMs:** the request bits (index, item IDs, prices). Two small side RAMs give `index[3:0]` and the slot's item ID as RAM outputs, which then act as address bits for the state and window RAMs.
- **Controller ROM:** a 410-state microcode sequencer. It runs the moving-average update for slot 1, then slot 2, then sends the response one bit per bit tick (start, 8 data bits, stop, 11 idle bit-times between bytes).
- **ALU ROM:** a 16K-entry lookup table that does one bit of work per clock: add/subtract with carry, compare, OR-reduce, and the BUY/SELL/repeat decision. Its flags feed back into its own address.
- **Per-item state RAMs:** running sum (20 bits), previous price, last action. Addressed by item ID, so routing is by item ID only.
- **Window RAM:** the last 16 prices per item, addressed by item ID and `index[3:0]`.
- **Algorithm per slot:** check `index == 0` (reset the sum) and `index < 16` (warm-up: window slot treated as empty, action NONE). Then `new_sum = sum - oldest + price`. Compare `prev` with `sum >> 4` and `price` with `new_sum >> 4`. BUY if `prev <= old_avg && price > new_avg`, SELL if `prev >= old_avg && price < new_avg`, otherwise repeat the last action. Finally store the price as `prev` and into the window.
- **Status LEDs:** `led0_n` and `led1_n` are unused and driven high.

The ROM contents are generated by `tools/gen_top.py`, which writes `src/top.v`. `src/top.v` is the complete source; the generator is included only so the tables can be inspected or rebuilt.

## Fixed UART Interface

The design follows the official interface:

```text
PC -> FPGA:
[index16][item1_8][price1_16][item2_8][price2_16]

FPGA -> PC:
[index16][item1_8][action1_8][item2_8][action2_8][reserved16]

reserved = 0x0000

ITEM_A = 0x11
ITEM_B = 0x22

NONE = 0x00
SELL = 0x01
BUY  = 0x02

UART = 115200 baud, 8N1, LSB first
Packet size = 8 bytes each direction
Multi-byte fields = big-endian
Routing = by item ID; response mirrors request slot order
```

## Judging Metrics / Results

> Official judging uses one 100-packet run (indices 0–99): 84 scored packets and 168 scored actions.

### Correctness

- Local test used: `22_robust_uart_test.py`
- Packet correctness (out of 84): 84
- Action correctness (out of 168): 168
- Estimated correctness points from `trade_summary_100.txt` (out of 70): 70.0

### Latency

- Average measured round-trip latency: 5.91 ms (macOS host)
- Idle time or buffering between response bytes (BL616 workaround): 11 idle bit-times (about 95 µs) between response bytes
- Test/setup used: `22_robust_uart_test.py`, MacBook Pro over the board's USB-C port
- The first packet of a run comes back in about 1.4–2.7 ms. Later packets take about 5.9 ms because the board's USB bridge (BL616) holds the reply before passing it to the PC. A test build that finished its reply 1 ms sooner (it started echoing before the request ended and dropped the idle gaps) measured the same 5.9 ms median, so the remaining latency is set by the bridge, not by the FPGA design.

### Logic Usage

From **Synthesis Report → Resource → Resource Usage Summary** and the Place & Route report:

- **Logic (LUT + ALU + ROM16 + SSRAM): 0**
- LUT: 0, ALU: 0, ROM16: 0, SSRAM: 0
- **Registers: 0**
- BSRAM: 32 of 46 (allowed and not counted as logic)
- Timing met: Fmax about 137 MHz vs 27 MHz.

Earlier versions of this design used 374, 178, 64 and 1 LUTs (the 1-LUT version used about 290 ALU cells and 552 registers).

## Known Limitations

- Item routing uses bit 0 of the item byte, which assumes the fixed IDs 0x11 and 0x22.
- The UART stop bit is not checked.
- A partial packet is discarded after about 18.7 ms of silence.
- Receive sampling uses a fixed 3-ticks-per-bit grid, which relies on the BL616's accurate 115200 baud rate.
- The receive pin feeds the block RAMs directly, with no synchronizer flip-flop. The receive state machine is encoded so that the only states that read the pin differ by a single bit, so a sample taken exactly on an edge can only land in one of two valid states.
